# Does hand-written DSP survive contact with a real model?

**Swapping Aurora's from-scratch audio front end into OpenAI Whisper, and measuring word error rate on LibriSpeech.**

Garfield Wang · November 2026 · repository: [`djzoom/AURORA`](https://github.com/djzoom/AURORA)

---

## TL;DR

Aurora's Audio Core is a NumPy-only reimplementation of the classic speech
front end: FFT, STFT, mel filterbank, log-mel, DCT-II and MFCC, written from
the definitions rather than imported from librosa or SciPy. Until now its only
evidence of correctness was unit tests against synthetic signals. This report
adds two empirical checks on real LibriSpeech audio:

1. **Numerical alignment.** Every primitive agrees with librosa / `numpy.fft`
   to floating-point precision (FFT and STFT to ~1e-16 relative; mel, MFCC and
   the full Whisper feature pipeline to the float32 rounding of the reference
   library).
2. **End-to-end substitution.** When Whisper's own feature extractor is
   replaced by Aurora's — same model weights, same decoder, different DSP —
   Whisper `base.en` produces **identical transcripts on 200/200** LibriSpeech
   test-clean utterances (30 minutes of speech), with a corpus WER of 3.08 %
   either way; `small.en` likewise gives 200/200 identical transcripts at
   1.76 % WER.

The interesting part was not the final table but the three places where a
"textbook" implementation silently diverges from what a production model was
actually trained on. Those are documented in §4.

All numbers can be regenerated with two commands (§6).

## 1. Motivation

> *[Section to be written by the author in his own voice: why build the DSP
> layer by hand, and what question this experiment answers. ~150 words.]*

The narrow technical question is simple. Aurora's rule is *no API wrappers*:
the point of the project is to understand audio ML from the sample up. But
"I implemented the FFT" is a weak claim if the only thing that has ever
consumed its output is a test comparing it to `numpy.fft` on a sine wave.
The stronger claim is: *a real, frozen speech model cannot tell the
difference*. That is a falsifiable statement, and this report tests it.

## 2. Setup

### 2.1 The system under test

`aurora.audio` (≈840 lines of NumPy including docstrings):

| Primitive | Implementation |
|---|---|
| DFT / FFT / IFFT | textbook DFT as a matrix multiply; iterative radix-2 Cooley–Tukey FFT with bit-reversal |
| Windows | Hann / Hamming / Blackman from the cosine-sum definitions, periodic and symmetric |
| STFT | strided framing with reflect padding; one `rfft` per frame |
| Mel scale | HTK formula (`2595·log10(1+f/700)`) and, new in this work, the Slaney scale (linear below 1 kHz, logarithmic above) |
| Mel filterbank | triangular filters from `n_mels + 2` equally spaced mel points; optional Slaney unit-area normalisation |
| DCT-II / MFCC | orthonormal DCT-II from the cosine basis; MFCC = DCT(log-mel) |
| Whisper front end | `aurora.audio.whisper_frontend.log_mel_whisper`: the exact Whisper recipe assembled from the primitives above (§4) |

NumPy is used as an array container and for elementwise arithmetic only. No
`numpy.fft`, `scipy.signal`, `librosa` or `torch` appears in `src/aurora/audio`.

### 2.2 Data

LibriSpeech `test-clean` (Panayotov et al., 2015), 16 kHz read speech,
2 620 utterances. Alignment checks use the first 20 files in sorted order;
the WER experiment uses the first 200 utterances in sorted order that are
≤ 30 s long (1 800 s of audio in total). No selection beyond that.

### 2.3 Reference implementations

- `numpy.fft.rfft` (float64) for the FFT.
- `librosa 1.0.0` for STFT, mel filterbanks, mel spectrogram and MFCC.
- `openai-whisper 20250625` for `log_mel_spectrogram` and `mel_filters`
  (Whisper computes features in float32 on top of `torch.stft` and a
  filterbank it ships as `mel_filters.npz`, itself generated by librosa).

### 2.4 Models and decoding

Whisper `base.en` (74 M parameters) and `small.en` (244 M), greedy decoding
without timestamps, `fp16=False`, CPU. Each utterance is padded to 30 s and
decoded **twice with the same model instance**: once on Whisper's own
features, once on Aurora's. Hypotheses and references are passed through
Whisper's `EnglishTextNormalizer` before scoring. WER is computed by
`aurora.speech.corpus_wer` (Levenshtein edit distance on word lists, written
from scratch, pinned to known cases in `tests/speech/`).

Environment: Python 3.13, NumPy 2.5, torch 2.5.1 (CPU), 2 vCPU container.
Runtime: ≈7 min for 200 utterances with `base.en`, ≈20 min with `small.en`.

## 3. Results

### 3.1 Numerical alignment on real audio

Maximum error over 20 LibriSpeech files (per-primitive worst case):

| Primitive | Reference | Max abs error | Max rel error |
|---|---|---|---|
| `rfft` (1024-point) | `numpy.fft.rfft` | 3.3e-16 | 3.5e-16 |
| \|STFT\| (n_fft 1024, hop 256) | `librosa.stft(pad_mode="reflect")` | 1.6e-14 | 4.0e-16 |
| mel filterbank, HTK, unit-peak | `librosa.filters.mel(htk=True, norm=None)` | 3.0e-08 | 3.0e-08 |
| mel filterbank, Slaney, unit-area | `librosa.filters.mel()` (defaults) | 1.3e-09 | 5.2e-08 |
| Whisper filterbank (80 × 201) | `whisper.audio.mel_filters` | 1.3e-09 | 5.2e-08 |
| mel spectrogram (HTK) | `librosa.feature.melspectrogram` | 6.9e-05 | 2.8e-08 |
| MFCC (13 coefficients) | `librosa.feature.mfcc` | 2.8e-07 | 7.8e-10 |
| **Whisper log-mel, end to end** | `whisper.log_mel_spectrogram` | 2.7e-05 | 2.2e-05 |

Reading the table: the transforms Aurora computes in float64 against float64
references (FFT, STFT) agree to machine precision. Everything below the line
is compared against a **float32** reference — librosa returns float32
filterbanks and Whisper runs its whole front end in float32 — so errors of
1e-8 to 1e-5 are the reference's own rounding, not Aurora's. The Whisper
end-to-end residual (2.7e-05 on features that live in roughly [−1.5, 0.5])
is consistent with float32 accumulation through a 400-point STFT.

### 3.2 Whisper with its front end swapped

| Model | Utts | Audio | WER (Whisper front end) | WER (Aurora front end) | Identical transcripts | Max feature Δ |
|---|---|---|---|---|---|---|
| `base.en` | 200 | 1 800 s | **3.08 %** | **3.08 %** | **200 / 200** | 2.9e-05 |
| `small.en` | 200 | 1 800 s | **1.76 %** | **1.76 %** | **200 / 200** | 2.9e-05 |

For both model sizes, not only is the corpus WER identical; every one of the
200 hypothesis strings is byte-for-byte identical after normalisation. The 77 utterances on which
`base.en` makes errors (e.g. *ardor → order*, *sodality → so dality*) make
exactly the same errors with Aurora's features. The model cannot tell the
two front ends apart.

For calibration, 3.08 % on this 200-utterance subset is in line with the
published `base.en` result on the full test-clean set (≈4.2 % with the same
normaliser); the subset is slightly easier than the full set and no claim is
made about the subset beyond the paired comparison.

## 4. What had to change, and why it matters

The textbook front end and Whisper's front end are not the same thing. Three
discrepancies had to be resolved before the swap worked, and each is a
concrete lesson about the gap between "understanding the algorithm" and
"matching a trained model".

**4.1 A 400-point FFT is not a 512-point FFT.** Whisper frames audio with
`n_fft = 400` and calls `torch.stft` directly on 400 samples. Aurora's
radix-2 FFT needs a power of two, and the original `stft` silently
zero-padded 400 → 512. Zero-padding does not change the spectrum's
*information*, but it changes its *sampling*: 257 bins at 31.25 Hz spacing
instead of 201 bins at 40 Hz. The mel filterbank Whisper was trained with
expects 201 bins. Feeding it a 257-bin spectrum is simply a shape error;
re-deriving a 257-bin filterbank gives *a* mel spectrogram, but not the one
the weights were fit to. The fix was to compute the 400-point transform from
the DFT definition as a single `(frames × 400) @ (400 × 201)` matrix product
(`rdft_frames`). For 3 000 frames this costs about 2.4 × 10⁸ complex
multiply-adds — negligible next to the model — and it is still "from
scratch".

**4.2 HTK mel ≠ Slaney mel.** Aurora used the HTK formula
`2595·log10(1 + f/700)` with unit-peak triangles, which is what most
textbooks give. librosa's default — and therefore the filterbank baked into
Whisper's checkpoint — is Slaney's: linear below 1 kHz, logarithmic above,
with each triangle scaled to unit *area* rather than unit *peak*. The two
scales place filter centres differently across the whole band, and the area
normalisation changes band energies by a frequency-dependent factor. The
filterbank module now exposes both (`htk=True/False`, `norm=None/"slaney"`),
and the Slaney variant reproduces Whisper's `mel_filters.npz` to 1.3e-09.

**4.3 Edge frames: reflect vs zero padding.** The first alignment run showed
the STFT disagreeing with librosa by 0.2 absolute — on *edge frames only*.
librosa changed its default centre padding from `reflect` to `constant`
(zeros) in 0.10; Aurora, like Whisper's `torch.stft`, reflect-pads. Interior
frames were already identical. This is a reminder that "matches librosa" is
version-dependent, and that the edge-frame convention is a real design
choice that affects the first and last ~12 ms of every utterance.

**4.4 The normalisation tail.** Whisper's recipe after the mel projection is
`log10(max(x, 1e-10))`, then clamp to `max − 8`, then `(x + 4) / 4`; it also
drops the final STFT frame so that 30 s yields exactly 3 000 frames. None of
this is "DSP" in the textbook sense, but all of it is load-bearing: the
clamp and affine map put features in the range the encoder's first
convolution expects. Omitting any step produces features that look fine on a
plot and transcribe badly.

## 5. Limitations

- **Scope.** This validates the *front end* only. Aurora does not yet contain
  a trained acoustic model; the decoder, encoder and weights are Whisper's.
  The result says "the hand-written DSP is indistinguishable from the
  reference", not "Aurora can do ASR".
- **One dataset, clean speech.** LibriSpeech test-clean is read English audio
  with high SNR. Edge-frame and padding conventions could matter more on
  short or noisy segments; this was not tested.
- **Subset, not full set.** 200 of 2 620 utterances, chosen by sort order
  rather than at random. The paired comparison (same utterances, same model)
  is unaffected by this, but the absolute WER should not be quoted as a
  test-clean number.
- **Greedy decoding.** Beam search with temperature fallback (Whisper's
  default in `transcribe`) could in principle amplify 1e-5 feature
  differences into different beams. It was not run.
- **Float32 reference.** The 2.7e-05 end-to-end residual is attributed to
  the reference's float32 arithmetic. This is plausible but was not proven
  by, for example, re-running Whisper's front end in float64.
- **Compute.** Everything ran on 2 CPU cores. Larger models (`medium`,
  `large-v3`, which uses 128 mel bins) were not tested for time reasons; the
  code supports `n_mels=128`.

## 6. Reproducing

```bash
pip install -e ".[dev]" librosa openai-whisper soundfile torch
curl -LO https://www.openslr.org/resources/12/test-clean.tar.gz && tar xzf test-clean.tar.gz

python scripts/bench_alignment.py   --librispeech LibriSpeech/test-clean --n-files 20
python scripts/bench_whisper_swap.py --librispeech LibriSpeech/test-clean --model base.en --n-utts 200 --out results/base.en
```

Outputs land in `results/` as Markdown tables, JSON summaries and a
per-utterance CSV (`whisper_swap.csv` contains every reference, both
hypotheses and both per-utterance WERs). `pytest` runs the 92 unit tests,
including the new Whisper-front-end and WER tests, with NumPy as the only
dependency.

## 7. Next steps

The natural continuation is to replace the next stage of the pipeline rather
than the first: a CTC/Conformer acoustic model trained on LibriSpeech
`train-clean-100`, scored with the same `corpus_wer`, with Aurora's front end
as the feature extractor. That turns "the model cannot tell the difference"
into "the model was trained on these features". The roadmap for that lives in
`ROADMAP.md`.
